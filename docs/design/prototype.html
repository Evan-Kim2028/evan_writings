GLM-5.3-Flash has large provider cache-hit variance

Cache hit rates on OpenRouter ranged from 80% on Z.AI to 0% on DeepInfra and Fireworks. Quality clustered. Cost did not follow cache, because output tokens dominate this workload.

Evan Kim·7 min read· #inference#openrouter#data-pipeline-eval
TL;DR

GLM-5.3-Flash was measured across five OpenRouter providers on a lakehouse repair gym. Cache hit rates ran from 80% (Z.AI) to 0% (DeepInfra, Fireworks). Pass stayed between 53% and 62%. Cache did not order the bill: prompt cache only discounts input, and output tokens dominate this workload.

GLM-5.3-Flash, released 26 August 2026 (Z.AI), was measured across five providers on OpenRouter on a custom data pipeline evals dataset. The results showed significant variance across all of the providers.

Although quality clustered, where every provider passed 53%–62% of tasks, the cache hit rate and end cost did not cluster. The most striking observation was that Z.AI had the highest cache rate, at 80%, across all five providers.

The variance is because GLM-5.3-Flash is an entirely new hybrid linear + sparse attention architecture that requires a different inference stack. Linear layers keep a running state for nearby tokens. Sparse layers keep a smaller KV and an indexer for the rest of the context. The effective cached-input discount is

$$\text{cost} = p_{\text{in}}\,(1-h)\,T_{\text{in}} + p_{\text{cache}}\,h\,T_{\text{in}} + p_{\text{out}}\,T_{\text{out}}$$

where $h$ is the cache hit rate. With $T_{\text{out}} \gg T_{\text{in}}$ on this workload, $h$ barely moves the total.

Provider benchmark results

The providers were benchmarked on data-pipeline-eval, a small public gym of lakehouse incidents taken from personal production repairs where agents predictably fail. Click a column header to sort.

The nine jobs sit in four categories.

  • Serving. The next run treats the wrong thing as current or done. Watermarks advance before commit.
  • Incremental I/O. A cheap probe plans a full scan, or a retry starts at record one.
  • Schema. Schema and field identity drift across runs.
  • Time. The wrong clock closes the window.

     .agg(hit=pl.col("cache_tokens").sum() / pl.col("input_tokens").sum(),

Why cache hit rates differ

Cache efficiency depends on the provider inference setup. Z.AI scored highest because they built a custom inference stack around the caching requirements of 5.3-Flash. A cache hit requires the next request to reach a replica that still holds the cached state. A provider can have a working prefix cache and still get poor hit rates if requests move between replicas.

The provider needs to manage the model's cached state, keep the relevant replicas warm, and route repeated prefixes back to the right replica.

What this costs

The significant cache hit difference did not translate into a significant cost difference. Hover the points.

Prompt cache only discounts input. Input size is almost the same on every provider, about 19k to 20k tokens across the 45 calls, and the rest is output. Novita produced 52k output tokens and DeepInfra 30k.
